# LaTeX resume editing and the view loop

This reference covers the "edit the resume directly, only the necessary parts, then view
it" workflow. Read it when the user has a `.tex` resume and wants tailored edits applied
in place rather than a fresh document.

## Golden rule: minimal diffs, never a rewrite

A resume `.tex` encodes hours of careful formatting: custom macros, spacing, alignment,
page-fit tuning. Regenerating the file destroys that. So edits are always **targeted
string replacements on individual content lines**, never a rewrite of the file.

Concretely:
- Edit only the text inside content commands: `\resumeItem{...}`, `\item ...`,
  the skills line, a `\project{...}{...}` heading, bullet text.
- **Never touch the preamble**: `\documentclass`, `\usepackage`, `\newcommand`,
  `\titleformat`, margins, spacing definitions. If a change seems to require preamble
  edits (new package, macro), stop and ask the user first, because it affects the whole
  document's fit.
- Preserve surrounding whitespace and the command wrapper exactly. Replace what's
  *inside* the braces, keep the braces and indentation.

## Locating what to edit

Before editing, read the `.tex` and map its structure so edits are precise:

1. Find section headers (`\section{...}`, `\resumeSection`, or the template's macro).
2. Within Projects/Experience, list each entry heading and its bullet lines. Common
   bullet macros: `\resumeItem{...}`, `\item`, `\cvitem`, `\bullet`.
3. Find the skills line(s), usually near the top, holding comma-separated keywords.

Match each intended change to one exact anchor string that appears once in the file, so
the replacement is unambiguous. If an anchor isn't unique, extend it with adjacent text
until it is.

## What edits to make (and the honesty guardrail)

Drive edits from the keyword-match output (`keyword_match.py`) and repo evidence
(`analyze_repo.py`):

- **Swap a weak bullet for a stronger, JD-tailored one** using bullets generated by the
  main skill. Keep the same `\resumeItem{...}` wrapper; replace only the sentence.
- **Add a project entry** when a repo produces a resume-worthy project the resume
  lacks. Copy the template's exact entry structure (heading macro + item list) from an
  existing entry so formatting matches, then fill it in.
- **Close keyword gaps in the skills line** only for keywords that are *truthful*, i.e.
  `repo_can_support: true` in the match output, or the user confirms real experience.
  Add them in the natural category (Languages/Frameworks/Tools). Never keyword-stuff and
  never add a language the user can't defend in an interview.

If the biggest missing keywords are things no available repo can back (e.g. a Google SWE
JD wants C, C++, Java, data structures, algorithms and every repo is JS/TS web work),
say so plainly and ask whether the user has a different repo, coursework, or experience
that shows them, rather than faking coverage. An honest 40% is safer than a stuffed 80%.

## Page-fit awareness

Resumes are length-sensitive (usually one page). Adding a bullet or project can push to a
second page. After edits, compile and check the preview:
- If it overflowed, tighten by shortening the newly added lines or, with the user's
  okay, trimming a weaker existing bullet. Prefer swapping over adding when space is
  tight.

## Compile and view

Use the render helper to build the PDF and produce preview images:

```bash
python3 ${CLAUDE_SKILL_DIR}/scripts/render_resume.py path/to/resume.tex
```

Output goes to `build/` next to the `.tex` (override with `--outdir`). It returns JSON
with the `pdf` path, `pages`, `previews` (PNG paths) and `warnings`. Show the preview image
inline so the user sees the result, and flag it if `pages` is over 1. On failure it returns `log_tail`; read it, fix the
offending line (usually an unescaped `%`, `&`, `_`, `#`, or `$` in newly inserted text),
and recompile. Remember to escape those characters in LaTeX content: `\%  \&  \_  \#  \$`.

If no LaTeX engine is installed in the user's environment, tell them: install a TeX
distribution (`tectonic` is the lightest, a single binary; or MacTeX / TeX Live), or
compile on Overleaf. The helper tries `latexmk`, then `pdflatex`, then `tectonic`. With
tectonic it compiles a temporary copy with fontawesome5 swapped out (it crashes tectonic on
some machines), so icons show as arrows in the preview; the user's `.tex` is never changed.

## The full loop

1. `analyze_repo.py` on the repo → evidence.
2. `keyword_match.py --jd JD --resume resume.tex --repo-json repo.json` → coverage +
   which gaps are honestly closable.
3. Generate tailored bullets (main skill) and apply them as **minimal str_replace edits**
   to the `.tex`, plus truthful skills-line additions.
4. `render_resume.py` → compile, show preview, confirm one-page fit.
5. Re-run `keyword_match.py` on the edited resume → show before/after coverage.
6. Report what changed, what's still missing and why, and any numbers the user must
   confirm before sending.
